CVE-2026-109618 php2shell 漏洞分析与复现

发表于2026-10-22|更新于2026-10-22|科普安全
|总字数:4.4k|阅读时长:14分钟|浏览量:

一、这个漏洞是什么

CVE-2026-109618 和 CVE-2026-109619 是 PHP 在 2026 年 10 月披露的两个内存破坏漏洞，公告给出的 CVSS 评分是 9.2。

影响范围是 8.5.11、8.4.26、8.3.35、8.2.34 及以下版本。修复版本分别是 8.5.12、8.4.27、8.3.36、8.2.35。7.4 及更早的分支已经停止维护，没有补丁。

它的特殊之处在于触发位置。漏洞不在某个框架或某个应用里，而在 PHP 自己的 multipart 解析器里。只要进程在处理上传请求，并且开启了上传进度功能，就可能被触发。目标页面写什么代码不重要，甚至不需要有业务逻辑。

攻击者不需要账号，也不需要用户点击。一个普通的 POST 请求就够了。

本文只做两件事。一是从 PHP 源码讲清楚这个漏洞怎么形成，二是记录我在容器里做的一次复现。文中所有偏移都取自这次使用的镜像，只对那个版本有效。

二、漏洞原理

2.1 请求在模块初始化之前就被解析

PHP 处理一个请求时，php_request_startup 里有一段固定顺序。

POST 的读取发生在 sapi_activate() 里。main/SAPI.c 第 463 到 469 行，只要开启了 enable_post_data_reading，并且请求带 POST 数据，就立刻调用 sapi_read_post_data()。

之后的顺序在 main/main.c 第 1873 到 1874 行。

zend_activate_modules 才是各模块的 RINIT。也就是说，表单解析发生在模块初始化之前。解析器此时已经在处理用户输入，会话模块却还没完成初始化。

8.5.11 的行号往后移了，顺序没有变。这个顺序是后面所有问题的前提。

2.2 上传进度把会话提前拉起来

session.upload_progress.enabled 默认是开着的。前端上传文件时，请求里会带一个 PHP_SESSION_UPLOAD_PROGRESS 字段，PHP 要记录进度，就得先把会话打开。

ext/session/session.c 的 php_session_initialize 做了这几件事。

如果请求里没有有效的会话 ID，就新建一个，并把 send_cookie 置 1，意思是稍后要把这个 ID 写进响应头。

会话 ID 的值来自哪里，由 session.use_strict_mode 决定。默认是 0，也就是不校验客户端给的 ID 是否由服务端签发过。客户端可以自己指定一个。

2.3 内存在半路耗尽

解析器一边读表单，一边往内存里存字段。如果请求体比 memory_limit 大，解析到一半就会耗尽内存，触发 bailout。

这个 bailout 不是事务性的。已经写进全局状态的字段不会回滚，已经分配的内存也不一定按正常顺序释放。具体到会话这块，会出现两个后果。

一是 PS(id) 指向的字符串可能在清理中被释放，指针却还留着。下次再读，就是一块已经不属于它的内存。

二是 PS(send_cookie) 还是 1，但因为前面已经输出过警告，响应头发不出去。php_session_send_cookie 在 session.c:1432 检查 SG(headers_sent)，发现已经发送就返回失败。这个待发送的状态留在了进程里，等下一个请求。

2.4 下一个请求把指针变成可控数据

第二个请求要做的事，是把一块可控内容放到悬空指针指向的位置。

Zend 的字符串结构在 Zend/zend_types.h 里定义。

PS(id) 指向的是 val，长度字段 len 在它前面 8 个字节。如果第二个请求能让一个数组的头部正好覆盖这段地址，那么读 len 的时候，读到的就是数组结构里的某个字段。

构造得当的话，这个字段是 nTableSize，值是 512。

图四：字符串头和数组头重叠之后，长度字段读到的是数组的 nTableSize。

PHP 接着会按这个长度做 URL 编码，代码在 session.c:1447。

它以为会话 ID 有 512 字节，就把后面 512 字节的内存原样编码，写进 Set-Cookie。这 512 字节里有函数指针，也有堆地址。

这一步是整个链条的分水岭。没有地址泄漏，攻击者只能猜，而 64 位地址空间里猜中的概率可以忽略。

2.5 从地址泄漏到函数调用

泄漏出来的内容里，有 pDestructor 指针，它指向 zval_ptr_dtor，减去这个镜像里的偏移就是 libphp 的基址。还有一批堆指针，按页对齐取多数票，能得到 Zend 内存池的基址。

有了这两个地址，就能伪造结构了。

Zend 的数组在销毁时，会遍历每个 bucket，调用数组自己保存的析构函数。

pDestructor 是一个函数指针，参数 zv 指向 bucket 里的 zval。把它改成 system，把 zval 的内容改成命令字符串，销毁数组时就等于调用了 system("...")。

内存耗尽之后有两条路能走到这个调用点。

一条是未初始化的 bucket。解析器在内存不足时中断，一个 bucket 已经挂进哈希表，内容还没写。关闭阶段遍历时把它当成正常 zval，里面的值被解释成指针，形成假数组，最后落到 pDestructor。

另一条是悬空的 zend_reference。会话的 http_session_vars 在 bailout 后留下一个指针，下一个请求用一个 31 字节的字符串占回那块内存，引用被伪造成可控结构，销毁时同样落到 pDestructor。

两条路的终点一样，区别在分配器和目标函数。我这次复现的是第一条。

图二：请求进入 php_request_startup 后，解析、会话初始化、内存耗尽都发生在同一个窗口，间接调用出现在请求关闭阶段。

2.6 为什么 disable_functions 挡不住

disable_functions 的实现方式，是在函数表里把对应项标记为禁用。PHP 代码调用 system() 时，虚拟机查表发现禁用就报错。

内存破坏利用不走这条路。它直接把函数指针改成目标地址，跳过去执行，中间没有经过函数表的检查。这次实验里 system、exec、shell_exec 全被禁用，命令照样执行了。

三、成因

把上面几步拆开看，成因有四层。

第一层是顺序问题。用户输入在模块初始化之前就被解析，解析器产生的中间状态没有模块来兜底。

第二层是错误处理问题。内存耗尽触发的 bailout 只保证不继续执行，不保证把已经改过的全局状态恢复原样。半初始化的会话、悬空的指针、待发送的 cookie，都是这么留下来的。

第三层是信任问题。关闭阶段遍历 HashTable 时，默认每个 bucket 都是有效 zval，不会检查它有没有被初始化。这个假设在正常情况下成立，在 bailout 之后不成立。

第四层是状态生命周期问题。会话是进程级全局状态，一个请求留下的残骸会被下一个请求读到。跨请求利用能成立，靠的就是这一点。

上传进度功能默认开启，只是把触发面放大了。关掉它能减少暴露，但没有修掉上面四层里的任何一层。

四、实际危害

漏洞成立时，攻击者拿到的是 Web 进程权限的代码执行。这次实验里是 uid=33(www-data)。

这个权限能做的事很具体。

读取应用配置。.env、config.php、数据库连接串、对象存储密钥、第三方 API token，通常就在 Web 目录或它的上一级。

写文件。往 Web 根目录写一个 PHP 文件，就得到可持续访问的 webshell，不依赖漏洞再次触发。

横向。拿到数据库口令后连内网数据库，拿到云厂商密钥后调云 API，拿到内网地址后做端口探测。

中断服务。这条链在执行后会崩溃当前 worker，反复触发就是拒绝服务。

如果目标在容器里，影响范围受容器限制。如果是传统的单机部署，Web 权限往往能读到同机的其他应用配置。

危害的另一面是门槛。这条链对配置有要求，不是所有 PHP 都中。

条件 要求 现实情况
PHP 版本 未修复分支 8.5.12 及以上不受影响
display_errors On 生产环境常设为 Off
memory_limit 小于请求体 线上常见 128M
post_max_size 大于触发字段 需要能收下大请求
worker 数 单 worker 更稳 多 worker 需要重试或轮换
地址来源 需要泄漏或标定 纯远程泄漏这次没打通

所以准确的表述是，内存破坏到代码执行这条路已经确证，在实验室条件下可以稳定复现。野外利用需要同时满足多个配置条件，还要解决地址随机化。它属于条件苛刻但后果严重的一类，不能写成默认配置下人人可打。

五、偏移是什么，为什么换版本就打不出来

程序加载到内存里，函数的位置不是一个固定数字。Linux 每次启动会给共享库一个随机的基址，这叫 ASLR。同一个函数，这次在 0x7f2a 开头，下次可能在 0x7f6f 开头。

函数相对库起点的距离是固定的，这个距离就是偏移。绝对地址等于基址加偏移。

图五：基址每次变，偏移在同一个构建里不变。换一个构建，偏移也会变。

编译器和链接器决定每个函数排在文件里的位置。源码变了、编译选项变了、链接的库变了，函数的大小和顺序都会变，偏移跟着变。版本号一样也可能不同，官方镜像的 8.5.11 标签在十月下旬换过一次构建，前后两个二进制的 zif_system 偏移就不一样。

利用链里有两类偏移。

代码偏移指向函数。比如 zif_system 在 0x5996e0，伪造的析构函数指针填基址加这个值。填错一个字节，调用会落到指令中间或者别的函数上，进程直接崩，命令不会执行。

数据偏移指向结构。伪造的数组要放在距离内存池基址 0x7e0d8 的位置，假引用要放在 0x7a6e0。这类偏移错了不一定立刻崩，而是读到错的数据。纯 HTTP 版本读出的长度在 262 到 706 字节之间跳，就是落点偏了。

确认偏移对不对，有个简单办法。泄漏出来的指针，低 21 位应该等于目标符号偏移的低 21 位。库基址按 2MB 对齐，低 21 位就是符号在库内的指纹。对不上，要么泄漏错了，要么二进制不是这个版本。脚本里报的 LIBPHP_PTR_INVALID 就是这个检查。

取偏移用 nm。zif_system 是本地符号，用不带 -D 的 nm 才能看到。

这次用到的几个值。

这些值只对 php@sha256:974e3a92… 这个构建有效。换镜像、换发行版、换编译参数，都要重新取。

六、复现

这两个值就是我这次用的偏移。换一个构建，它们会变，后面所有地址计算都要重新取。

6.2 部署

先准备一个最小的目标页面和配置文件。

启动容器。不发布端口，只挂在内部网络上，宿主机要访问时另接一条通道。

Apache 要用 prefork，并且只留一个 worker。镜像默认是 prefork，把 StartServers、MaxRequestWorkers、ServerLimit 都改成 1。改完重启容器。

多 worker 时状态会被别的进程接手，复现不稳定。

图一：实验环境。宿主机通过 Docker 内部网络访问容器，php.ini 和目标页面只读挂载。

6.3 三个请求

复现脚本要构造三个请求，顺序不能乱。

准备请求带一千零一个普通字段，触发 max_input_vars 的上限，同时带一个 PHPSESSID 为空的 cookie，一个上传进度字段，一个很小的文件字段，最后是一个二十四兆的普通字段。内存在这里耗尽，会话状态留在悬空的位置。

占位请求带一千个字段，其中一个字段是两百五十七个元素的数组。数组的头部要落在悬空指针前面，把长度字段盖成 512。

触发请求带伪造好的结构，把析构函数指针指向目标函数，把命令字符串放进对应的位置。

三个请求都是普通的 multipart POST，目标页面只有一行 echo。中间不需要登录，也不需要页面配合。地址标定用 gdb 完成，这一步是实验辅助，不是攻击链的一部分。

七、没有打通的部分

不依赖调试器的版本我也试过。思路是用前两个请求把地址泄漏出来，后两个请求完成伪造，全程不开 gdb。

结果不稳定。准备请求的内存耗尽点落在 6296371 字节，和标定时不一样。占位请求读出的长度在 262 到 706 字节之间跳，没有出现 512。把数组落点附近的位置逐个试过，始终差一点。

原因在堆布局。悬空指针的位置和后续分配的位置，受前面所有请求的影响，换个环境就变。我这次没有继续把差异定位到具体的分配调用。

这一节写出来，是想说明前面那个结果不是随手就能复现的。它依赖调试器标定，也依赖这台机器上的布局。

八、修复与检测

升级。8.5.12、8.4.27、8.3.36、8.2.35 已经修复。7.4 只能靠隔离和下线。

临时缓解。关掉 session.upload_progress.enabled，触发面会小很多。把 post_max_size 设成小于 memory_limit，解析阶段就不会因为大字段耗尽内存。这两条都只是绕开条件，不是修漏洞。

WAF 规则要改。很多规则按 Content-Type 里的 multipart/form-data; 匹配，PHP 还认逗号和空格。

按分号写死的规则，后两种直接过去。

检测思路。单次请求带超过一千个字段、超大 multipart 字段、异常 PHPSESSID，同时伴随 5xx 或 worker 重启，这几个信号放在一起看。单独看任何一个都容易误报。
