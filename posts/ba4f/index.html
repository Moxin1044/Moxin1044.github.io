【ArchLinux】ToDesk 在 GNOME Wayland 下屏幕共享授权框一闪而过：排查与修复记录

发表于2026-11-03|更新于2026-11-03|LinuxArchLinux桌面
|总字数:4.9k|阅读时长:18分钟|浏览量:

前言

同一台 Arch Linux 机器上，向日葵发起远程连接时，GNOME 的屏幕共享授权框会停住，等用户点一下“共享”。换成 ToDesk，授权框只闪一下，大约两三百毫秒就没了，手还没来得及移到按钮上；有时远端黑屏，有时连接刚建立又退回去。

下面这条记录来自一次完整排查。ToDesk 4.9.8.1 本身有 Wayland/PipeWire 抓屏能力；授权框闪一下，来自 AT-SPI 自动点击。另有一条会话创建失败链路，需要单独看。

环境：Arch Linux / GNOME 51.1 Wayland / mutter 51.1 / todesk-bin 4.9.8.1-1

摘要：本机日志表明，ToDesk 4.9.8.1 已具备 Wayland/PipeWire 抓屏能力。授权框一闪而过的直接原因，是 ToDesk 通过 AT-SPI 无障碍接口自动点击了“共享”按钮。为 xdg-desktop-portal-gnome 单独设置 GTK_A11Y=none，可以阻止这一步自动操作，让授权框保留到手动确认。此方案针对授权框被自动确认的问题；日志中的会话创建失败仍需单独排查。

图一：调整后的 GNOME 屏幕共享授权框，等待用户选择显示器并点击“共享”。自动确认的日志证据见第 3.1 节。

问题现象

在同一台机器上：

  • Sunlogin（向日葵）：发起远程连接时，GNOME 的屏幕共享授权框正常弹出并停留，手动点击“共享”后可以正常连接。
  • ToDesk：授权框只出现约 200–400 ms 就消失，来不及手动确认；有时远端黑屏，或连接刚建立便中断并重试。

  • AUR 的 todesk-bin 包在安装时还会打印一句：

这些现象很容易让人得出“ToDesk 不支持 Wayland，只能切换到 X11”的结论。不过，本机对 4.9.8.1 的排查表明：它已经具备 Wayland 抓屏能力，问题出在授权交互及后续会话建立环节。

原因分析：自动确认与会话创建失败

授权框一闪而过：ToDesk 通过 AT-SPI 自动确认

GNOME 的屏幕共享对话框由 xdg-desktop-portal-gnome 提供，其控件可通过 AT-SPI 无障碍总线访问。结合相关符号与运行日志，ToDesk 的 WaylandSecureUiController 会执行以下自动化操作：

  1. 连接 AT-SPI 无障碍总线；
  2. 在控件树里找到 portal 对话框；
  3. 检查或选中显示器，并自动点击“共享”按钮。

自动确认可以解释授权框为何迅速消失，却不能解释所有连接失败。排查中还遇到了连接反复重试、授权框反复弹出、远端始终没有画面的情况。

  2. ToDesk 自动点“共享”；

一种可能的解释是，重连时旧会话尚未完成清理，新会话便开始创建。不过，仅凭上述日志，还不足以确定是 ToDesk 的会话管理、Mutter 的状态限制，还是两者交互导致。可以确定的是：这属于会话建立阶段的故障，不能据此判断程序没有 Wayland 抓屏能力。

修复方案：关闭 portal 进程的无障碍桥接

原理

在这条自动化链路中，ToDesk 是 AT-SPI 的客户端，portal 对话框则由 GTK4 应用提供。让 xdg-desktop-portal-gnome 不再通过无障碍总线暴露控件，就能阻止 ToDesk 沿这条路径找到并点击“共享”按钮。

GTK4 用环境变量 GTK_A11Y 控制无障碍桥接：

  • GTK_A11Y=atspi：使用 AT-SPI 无障碍后端。
  • GTK_A11Y=none：关闭无障碍后端。

为 xdg-desktop-portal-gnome.service 添加 systemd 用户服务覆盖配置（drop-in），将该变量限定在 portal 进程内。

需要注意的点：

  1. 适用范围为本文记录的 GNOME 环境。 KDE、Hyprland 使用不同的 portal 后端和界面实现；GTK_A11Y 是 GTK 的设置，不能仅替换服务名就照搬本方案。
  2. 修改范围限于该 portal 进程。 其他应用的无障碍设置不变，但 Orca 等工具将无法通过该进程的无障碍桥接访问其界面。
  3. 授权需要手动完成。 ToDesk 等待响应存在超时限制，请及时选择显示器并确认。
  4. 会话创建失败需要单独排查。 本方案不保证解决 Session creation inhibited；遇到时可先尝试重新连接或重启 todeskd.service。
  5. 自动确认行为值得反馈。 日志显示 ToDesk 会代替用户点击“共享”，使原本等待人工确认的步骤被自动完成。可以将相关日志提交给 ToDesk，反馈这一授权交互问题。
  6. 升级后重新验证。 如果后续版本不再自动点击，可撤销此临时方案，恢复 portal 的无障碍功能。
  7. 日志位置：
    • 用户侧：~/.local/share/todesk/Logs/session_*.log、client*.log、*.xlog
    • 服务侧（root）：/var/log/todesk/servicer*.log
    • portal：journalctl --user -u xdg-desktop-portal-gnome
