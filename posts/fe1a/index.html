飞秋（FeiQ）3.0.0.2 协议缺陷分析：设备名册伪造与消息缓冲残留

发表于2026-10-16|更新于2026-10-16|安全漏洞分析
|总字数:3.1k|阅读时长:9分钟|浏览量:

飞秋（FeiQ）用过的都不陌生。机房、教室、不少单位的内部办公网里都有它：装完就能用，不用架服务器，不用注册账号，谁在线、谁坐在几号机，列表里一眼就看得见。对老师来说它是个省事的点名工具，对运维来说它是内网里一个常年开着 UDP 2425 的进程。

我最近拿它做了点协议层面的分析，顺手写了个内网设备探测的小工具。本来只想弄清楚一个问题：局域网里一台机器，是怎么被别的机器看见的。

结果在这个过程里撞见两件事。

一件在设计层面。设备名册的键值选错了，选成了源 IP。这意味着任何一台机器，只要往自己网卡上多挂几个地址，就能凭空在别人的列表里变出上百台设备。

一件在内存安全层面。一段消息缓冲区没有正确终止，导致一条短消息会把缓冲区里上一条消息的尾巴带出来。而那条消息，可能是别人发的。

两件都不是远程代码执行那个级别。但合起来，足够让一间教室的网络变味。

先把协议摊开

飞秋从 2012 年前后一直更新到现在，协议是私有的，但它有个可以顺藤摸瓜的祖先是 IPMSG（IP Messenger）。抓包看 3.0.0.2 广播出来的报文，结构上确实和 IPMSG 同源：一条 UDP 报文就是一整段可读字符串，字段之间用 # 和 : 分隔。

它分两段。# 之前是第一段，最多八个字段；: 之后是第二段，走 IPMSG 的格式。逐字段拆开是图一这个样子。

图里有两个字段值得单独说。

一个是 f5，它声明这条消息有多少字节。后面讲缓冲区的时候，它是主角。

另一个是命令字。这一步绕不开：只有用 32（IPMSG 里的 SENDMSG）发，对端才会真正把你登记进名册并回包确认；用 1（ENTRY）发，如果对端已经有一台设备顶着同一个源 IP，名册里就只保留一台。

样本本身没什么保护。FeiQ.3.0.0.2.exe，18,290,688 字节，PE32 未加壳（.text 段熵 6.43），MD5 BFEA3E87B66B4164BADD346DE8172A36。链接时间戳指向 2013 年 6 月，字符串里留着原始构建路径 F:\FeiQ2012\source\Client\FeiQClient\Win32\Release\FeiQ.pdb。用 IDA 打开，解析逻辑基本能读成伪代码。

缺陷一：名册的键值选成了源 IP

飞秋的好友表是按源 IP 建索引的。一个源 IP 对应一个账户，报文里那些字段（MAC、用户名、主机名）虽然都在，但都不参与身份判定。

这条约束是从实验里逼出来的，不是从代码里看出来的。第一版工具只换了 MAC 和源端口，结果对方列表里始终只有一台；后来把源 IP 换掉，设备数才跟着涨。

说人话：人家认的是「你从哪个地址来」，不是「你是谁」。同一台机器开一百个端口，来的地址还是一个，所以只算一台；反过来，一台机器挂上一百个地址，就成了一百个人。

实测这一条已经落地：单源 IP 配 100 个源端口，对端显示 1 台；伪造 100 个源 IP，100 台全部登记，抓包能看到对端逐个回 217:<MAC> 的上线握手。工具做的事其实很朴素。先探测目标走哪块网卡，在同一个网段里挑一段空闲地址，用 CreateUnicastIpAddressEntry 批量挂到网卡上，然后逐台发包。间隔太密会掉量（0.15 秒一台明显丢），拉到 0.3 到 1.0 秒就稳了。

这里要分清一件事：这不是内存漏洞，是协议设计上的信任模型问题。 补丁没法只打在一个函数里，它需要改协议的键值定义。

缺陷二：一段没有终止符的缓冲区

这个是真漏洞，而且复现很稳。

飞秋解析报文时，把消息正文拷进会话对象里一块 0x8000 大小的缓冲（偏移 +0x118）。反编译出来大概是这个形状：

三个问题叠在一起：

第一，缓冲区没有整体清空，只把首字节置了 0。a2+0x118 之后的内容还是上一次留下的。

第二，拷贝严格按报文字段声明的长度来，不保证以 \0 结尾。

第三，长度记账是「声明长度 + 1」，而实际写入的字节里并没有那个终止符，账和实际对不上。

消费方（聊天窗口和聊天记录）把这块缓冲当 C 字符串来读，一直读到遇到 \0 为止。于是当本次消息比上一条短时，多出来的那一截就是上一条消息的残留。

实测

手工构包，两台「设备」来自不同源 IP：

A LEAKA 127.0.0.62 SECRET-SECRET-SECRET-SECRET 24
B LEAKB 127.0.0.63 hi 2

B 的消息把 A 的机密内容带了出来。多出来的那 24 个字符，正好是 LEAKA 那条消息被截断后的尾部。

为什么能跨会话

关键在于这块缓冲不是「每个对端一份」。消息泵里那个会话结构是个栈上局部变量，每收到一个包就重新走一遍同一个函数，同一个栈槽位被反复使用。所以第 2 步里被带出来的残留，来源不限于 A，可能是任何一个之前的对端留下的。

发送端看不到自己造成了什么，泄漏发生在受害者这一侧。这一点决定了它的检测方式：得在受害者机器上抓包记录收到的正文，再跟窗口或历史里显示的内容比对，显示比报文长出来的部分就是泄漏的残留。

但我没能打通它。 用合法分片接巨型偏移（0x7FFF0000 那种）投递了多轮，目标进程没有崩。说明函数开头的状态判定（this+0x98、cmd != 0x7F 那几个条件）在拷贝之前就把流程挡回去了。所以这一条停在「已定位、未验证」，它不是本文的结论，我把它写出来是因为分析的边界应该被交代清楚，而不是把没打通的东西写成打通了。

危害

把上面几条按证据强度分三档。

先说已经证实的部分。

对端名册可以被任意主机批量伪造。攻击者不需要任何凭据，只要能往目标网段发包，就能让目标机器的飞秋列表里多出成百上千台设备，每台都能给他发消息。实测 100 个源 IP 全部登记成功。

消息缓冲区残留会跨会话泄漏内容，并且泄漏出来的片段会作为消息正文写进聊天记录，也就是说，受害者的本地记录会被别人的内容污染。这一点对做取证的人尤其难受：聊天记录的完整性不再可信。

有一类可以合理推断，但没有逐项实测。

在教室和机房这类场景里，上面两条会合成一个挺实际的干扰手段。飞秋在课堂上承担的是发文件、收作业、通知这些职能，一旦名册被灌进上百台陌生设备、每条都带一条消息，老师要用的那几台真实设备就被淹没了。这是这套协议的信任模型被利用后的自然结果，但具体影响到什么程度，取决于现场怎么用飞秋，我没有在真实教学环境里测过。

还有一类是推不出来的。

分片接收那处未校验偏移到底能不能构成真正的越界写，目前没有证据。在打通它之前，不应把它写成可用漏洞。

怎么修

按优先级排。

第一优先，消息缓冲区。拷贝前整块清零，或者拷贝后显式补终止符；长度记账和实际终止必须一致。

第二优先，分片接收。对偏移做区间校验，offset + size <= 缓冲长度，越界就丢弃并断开会话。顺带把所有「长度字段与长度比较」的地方统一改成无符号比较并显式判负。

第三优先，身份绑定。把 MAC、用户名与源 IP 做一致性校验，名册按 IP 加 MAC 双键索引，对「新上线的前端」加一次握手确认。这一条要动协议，改起来最重，但它是缺陷一的根。

发送端有个临时规避：把结尾的 \0 也算进声明长度，对端就会连终止符一起拷进去，字符串被正确截断。但这只是绕过，修不了别人机器上的同一个缺陷。

工具与复现

上面用到的东西整理成了一个仓库，C 语言写的，无第三方依赖，含投放与探测两套：

https://github.com/Moxin1044/feiq-virtual-devices

投放工具需要管理员权限，因为要往网卡上加源 IP；探测工具普通权限就行，支持主动扫网段和被动监听两种模式，后者只监听 UDP 2425 上的广播，不主动发包。

投放出来的设备是伪造的名册条目，不是真实节点，重启对端的飞秋就没了。

最后

分析这套东西的时候，反复出现的一个感受是：局域网软件的信任模型往往比它的代码质量更值得关心。

缓冲区那个缺陷是写代码时漏了一行，好修。而「谁在网段里发包，谁就是一台设备」这个假设，是从协议设计那一层带进来的，它决定了这个网络里「身份」这个概念本身有多重。答案是几乎没有重量。

文中的测试都在自有设备和自有网络里完成。伪造设备上线的做法会对别人的办公网络造成实际干扰，不要拿到没有授权的网段上试。
