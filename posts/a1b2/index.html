对 Dataman 的代码审计分析

发表于2026-10-16|更新于2026-10-16|安全代码审计
|总字数:4.3k|阅读时长:15分钟|浏览量:

Dataman 是一个开源的数据管理系统，README 里写得很克制：轻量、现代设计风格、移动端。功能清单列了二十来项，从配置管理到广告位，看得出是认真做的项目。技术栈是 Laravel 8 加 Dcat-Admin，代码量不大，一百五十个 PHP 文件、九千行左右。

我把它拉到本地跑起来审了一遍。结论不太好看：从打开登录页，到在服务器上执行系统命令，全程不需要任何已有的账号。

这篇文章记录审计过程。漏洞本身在报告里有逐条列出，这里更想讲的是怎么找到的、怎么判断的，以及中途两次差点把洞放过去的地方。

一、先摸清攻击面

拿到一个 Web 项目，第一步不是搜 eval，是先搞清楚它长什么样：用什么框架、路由怎么组织、哪些入口不需要登录。

Dataman 的框架信息在 composer.json 里：

Laravel 8 加 Dcat-Admin 2.x。项目自己的路由分两块，routes/api.php 里是给移动端用的接口，routes/web.php 是后台。

真正值得盯的是 routes/api.php 里的这一段：

这个路由组上没挂任何鉴权中间件。后台路由全都在 ['web', 'admin'] 中间件组里，而这两个接口是裸露的。

不过先别急着下结论。后台的路由虽然在中间件组里，但控制器构造函数里还能再挂，Dcat-Admin 和 Laravel 都习惯这么写，我见过不少项目是靠控制器里的 $this->middleware('auth') 兜底的。

二、汇点扫描很干净，但这不算好消息

第二步做汇点扫描，也就是直接搜危险函数，看用户输入有没有可能流进去。

结果很干净。原始 SQL 只有一处，是安装时导入 install.sql 用的。代码执行、反序列化、命令执行一个都没有。文件操作只有两处，一处在安装器里读 composer.json，一处在 MediaController 里读媒体文件。

这里有个判断要说清楚：汇点干净不等于没有漏洞。

Laravel 这类框架把危险操作包得很深。SQL 走 ORM 之后天然参数化，文件操作被 Storage 抽走，命令执行基本不会出现在业务代码里。真正的高频漏洞搬了家，跑到逻辑层面去了：谁能访问哪个接口、上传的文件是什么类型、模板有没有转义、配置项有没有关掉。

所以扫描只能排除掉一类情况，告诉你「不是那种一眼可见的洞」。接下来得换个方向找。

三、盯住用户输入流向文件系统的那一处

换个问法：用户能控制的数据，最后会到达哪里？

把所有从请求里取值的地方列出来，逐个往后追，看它最终被送进什么函数。

追完的结论是：整份代码里，用户输入与文件系统之间只有一条通路，就是媒体管理模块 MediaController。列表、下载、上传、删除、移动、建目录，六个动作全部把请求参数直接交给了 MediaService。

攻击面收窄到这一个文件上了。Dataman 的六个漏洞，有四个出在这里。

这里有个用词要较真。这类问题常被笼统地叫成「弱口令」，但不够准确。问题不在于口令强度低，admin 也不算弱到能被字典秒破的程度。真正的问题是它是安装器内置的、且没有人要求你改。只要部署方照着文档走完流程就上线，这个口令就会一直有效。准确的叫法是默认口令。

回到开头那两个没有鉴权的接口。

九、还有两个设计问题

审计里还看到两处不算漏洞、但值得写下来的东西。

一处是平台信息的缓存永不过期。PlatformService 的构造函数用一个锁控制全量刷新：

锁一旦写入就不再失效，代码里也没有任何在平台保存时清除它的地方。表现就是：后台新增一个平台，接口侧查不到，必须手动跑 php artisan cache:clear 才生效。反过来，删掉的平台在缓存有效期内还会继续对外服务。

另一处是操作审计日志默认关闭。项目带了 operation-log 扩展，中间件也写好了，但数据库里它的启用状态是 0，另有一份应用级的 LogOperation 中间件在全项目搜不到注册点。实测 admin_operation_log 表记录数为零，后台的所有操作都没有留痕。

这两条本身不构成漏洞，但会放大前面那些漏洞的后果。上传了 webshell 却没有审计记录，事后溯源就少了最直接的一条线索。

十、这次审计的几点归纳

把过程回过头看，有几个判断在下次能直接用上。

汇点扫描干净不等于没洞。框架把 SQL、文件、命令这些危险操作都封装了，扫描能排除掉一类问题，但真正的高频漏洞已经迁到逻辑层去了。扫完要换个方向，去看权限、文件类型、模板转义和配置项。

找攻击面的高效问法是「用户输入最后去了哪」。把所有从请求取值的地方列出来逐个往后追，通常能很快收窄到一两个文件。Dataman 一百五十个文件，最终六个漏洞里四个出在同一个控制器。

路径穿越的层级要数出来，不要心算。少一级的结果是 404，看起来和没有漏洞完全一样。

判定文件上传能不能导致命令执行，必须看三个条件：落在哪个目录、这个目录能不能从 Web 访问、Web 服务器会不会执行它。「不校验扩展名」只是第一步。

术语要较真。「默认口令」说的是安装器内置且没人要求改，「弱口令」说的是强度低，是两回事，定级和修复方向都不同。

十一、修复建议

按优先级排：

上传是首要的。加扩展名与 MIME 双重白名单，丢弃原始文件名改用随机名，并且把上传目录移出 Web 根目录。如果架构上改不了，至少在 nginx 里禁掉该目录的脚本解析：

默认口令其次。安装器不再写死账号，改成安装时强制设置，并加验证码与登录失败锁定。

文件读取给 file 参数做 realpath() 归一化，校验结果落在存储根目录之内，拒绝含 .. 的输入。更彻底的做法是改用文件 ID 索引寻址。

调试开关在生产环境必须关掉，.env.example 里的默认值也应该改成 false。同时补齐 channel 表缺失的列，让 schema 和代码对上。

XSS 那一处，把 preview 改成只含图标和链接 ID 的结构化数据，交给 Blade 正常转义。确需输出 HTML 时，对拼接进去的文件名和目录名统一做 e()。
